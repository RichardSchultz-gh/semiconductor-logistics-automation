= Eigenleistung Paul Marx

== Thema: Testorganisation im Rahmen einer iterativen Softwareenwicklung mit OpenUP

Bei der Entwicklung unserer Web-Anwendung stand die Testorganisation vor einer Vielzahl von Herausforderungen, die typisch für iterative Entwicklungsprozesse sind. Die iterative Entwicklung zeichnet sich durch wiederholte Zyklen von Planung, Design, Implementierung und Testen aus, die als Iterationen bezeichnet werden können. Die konkrete Problemlage bestand darin, dass auf geänderte Anforderungen reagiert werden musste  und neue Funktionen in kurzen Abständen implementiert und getestet werden mussten. Insbesondere mussten für die Strukturierung der Tests, das Zeitmanagement und die Kommunikation mit den Entwicklern Lösungen entwickelt werden.


Übergeordnet stellte sich bei der Organisation die Frage, in welche Teilbereiche die Tests inhaltlich untergliedert werden sollten. Hierfür habe ich die Tests eng an die Requirements aus dem 1. Semester geknüpft, da hier auch die wesentlichen Funktionalitäten der Software definiert worden sind, die auch getestet werden müssen. Folglich habe ich für jeden zuvor spezifizierten Use-Case einen eigenen Test-Case eröffnet (z.B. Test des link:https://github.com/leni04/i04-projekt-frau-holle/blob/main/docs/requirements/use_case_01.inc.adoc[Use Case 1 - Los starten]  im Testcase link:https://github.com/leni04/i04-projekt-frau-holle/blob/main/docs/test/test_case_UC01_Los_starten.adoc[Test Case UC01 - Los starten]). Für die systemweiten Anforderungen wurde analog ein separater link:https://github.com/leni04/i04-projekt-frau-holle/blob/main/docs/test/test_template.adoc[Test-Case] angeleg. Die einzelnen Tests innerhalb der Test Cases wurden mithilfe eines link:https://github.com/leni04/i04-projekt-frau-holle/blob/main/docs/test/test_template.adoc[Templates] standardisiert. Hier wurde für jeden Test die ID, der Zweck, die Testart, die Vorbedingungen, die Testdurchführung, die Nachbedingungen, die Eingabedaten, das Ergebnis, die To-dos und der Korrekturstatus festgehalten. Zusätzlich wurden beispielsweise Screenshots von Fehlermeldungen angehängt. Der einheitlichen und sauberen Dokumentation der Tests kam eine besondere Bedeutung zu, weil die Abweichungs- und Fehleranalyse von unserem Entwicklerteam durchgeführt worden ist. Es bedurfte also einer verständlichen Schnittstelle, welche Fehler unter welchen Bedingungen aufgetreten sind. Organisatorisch wurde daher, simultan zu den einzelnen Test-Cases, eine link:https://github.com/leni04/i04-projekt-frau-holle/blob/main/docs/test/Bugtracker.adoc[Fehlerliste] in gitHub geführt. Die Fehlerliste enthielt zu jedem Zeitpunkt eine Übersicht aller aufgetretenen Fehler sowie den aktuellen Bearbeitungsstand. In der Fehlerliste wurden dann die entsprechenden Dokumente und Test-IDs referenziert, sodass die Entwickler schnell in eine detailliertere Fehlerbeschreibung abspringen konnten. Zusätzlich fand die Kommunikation über eine Chat-Gruppe statt, in der sich über die Fehler augetauscht wurde.
Die Tests selbst wurden bei der Organisation in Unit-Tests und manuelle Tests unterteilt. Grund hierfür war, dass die Software auf der einen Seite eine vom Nutzer bedienbare Oberfläche bereitstellt, die sich für manuelle Tests anbot. Auf der anderen Seite gibt es als Akteur auch einen Timer, der zeitgesteuert einzelne Funktionen aufruft. Zum Test der jeweiligen Methoden und Klassen erschienen Unit-Tests geeignet. Hierbei konnten dann konkrete Methoden, wie das Starten von Losen getestet werden (z.B. Test von start_lot() im link:https://github.com/leni04/i04-projekt-frau-holle/blob/main/src/testing/TC_UC1_TID6.py[TC_UC1_TID6.py]). Für eine bessere Struktur und Organisation wurde auch auf Test-Suits zurückgegriffen (z.B. link:https://github.com/leni04/i04-projekt-frau-holle/blob/main/src/testing/Test_Suite_UC2.py[Test_Suite_UC2]). Diverse Architekturentscheidungen aus dem link:https://github.com/leni04/i04-projekt-frau-holle/blob/main/docs/architecture/architecture_notebook.adoc[Architecture-Notebook] hatten außerdem Einfluss auf die Unit-Tests. Diese mussten infolgedessen in Python geschrieben werden und SQL-Alchemy als Framework nutzen.
Der zeitliche Rhythmus der Tests wurde dabei stets durch das iterative Vorgehen mit OpenUp bestimmt. In jeder Iteration wurde somit neu festgelegt, welche Ziele erreicht und welche Tests durchgeführt werden mussten. Innerhalb jeder Iteration nutze ich zur Selbstorganisation ein Kanban-Board. Das Kanban-Board war ein nützliches Tool, um die ausstehenden Tests in bestimmte Phasen, wie "in Arbeit", "erledigt" oder "To-do" zu unterteilen und stets den Gesamtüberblick zu behalten. 


Grundsätzlich lässt sich sagen, dass die Testorganisation gut funktionierte. Unsere Webanwendung konnte infolgedessen vollumfänglich vor der Abnahme durch unseren Kunden getestet werden. Für zukünftige Projekte würde ich allerdings, zeitlich gesprochen, nicht nur parallel und nachgelagert zur Implementierung Tests durchführen. Um zeitliche Ressourcen effizienter zu nutzen, würde ich zukünftig auch auf die Praktik des Test-driven Developments zurückgreifen. Hierbei wird der jeweilige Test vor der zu testenden Klasse geschrieben. Dadurch kann eine gleichmäßigere Arbeitsauslastung beim Testen geschaffen werden. Außerdem können Fehler deutlicher früher im Entwicklungszyklus erkannt werden, was wiederrum hilfreich für die Entwickler ist. In Bezug auf die Inputs aus dem Fachaustausch Test würde ich das Testen einer Webanwendung in Zukunft auch nicht mehr manuell organisieren und durchführen, sondern ein automatisiertes Tool wie Playwirght verwenden. Hierbei ergeben sich beispielsweise Vorteile bei der Automatisierung komplexer Interaktionen, wie Dateiuploads, oder auch die Möglichkeit der Parallelisierung von Tests, sodass Laufzeiten reduziert werden können. Zusätzlich wäre es zumindest diskutabel bei künftigen Projekten die Kommunikation mit den Entwicklern vorranging über Issues in GitHub zu organisieren, die dem jeweiligen Entwickler für die Fehlerbehebung zugewiesen werden. Für unsere Fehleranzahl erwies sich ein Dokument als Fehlerliste als probates und schnelles Mittel, aber bei noch größeren und komplexeren Projekten könnte ein einzelnes Dokument vermutlich an Übersichtlichkeit verlieren.
